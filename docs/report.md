# レポート: 言葉で片付けてくれる SO-101(v1: シミュレーション)

Physical AI「AI×ロボティクスによる創造的タスクの実現」の課題。自然言語の指示(例:「赤いブロックを箱に入れて」)を VLM で解釈し、SO-101 が pick & place を実行する。

> **このレポートの範囲**: v1(MuJoCo のシミュレーションで完結)。**実機(SO-101)での動作と、v2(SmolVLA の微調整・IK 版との実機比較)は行っていない**。書いていないことは「未実施」と明記し、実測していない値は載せない。

## 1. 課題の概要

カメラ画像と指示文を VLM に渡し、返ってきた検出枠を 3 次元位置に直し、IK で軌道を作って、MuJoCo のシミュレーションで SO-101 に実行させる。成功は、ブロックが箱に入ったかで自動判定し、試行を繰り返して成功率を出す。

```
指示 ──▶ VLM(検出枠) ──▶ 画像+深度から 3 次元位置 ──▶ IK の軌道 ──▶ 安全フィルタ ──▶ 実行(MuJoCo) ──▶ 成功判定
```

## 2. 目的

- 「言葉で指示して、ロボットが動く」までを、**差し替えられる部品の組み合わせ**として作る(VLM、ロボット、方策をそれぞれ抽象の背後に置く)。
- VLM を複数社(Anthropic / OpenAI / Gemini / Gemma)で切り替え、**同じ条件で成功率と検出誤差を比較**できるようにする。
- 実機に差し替えられる構造にしておく(実機の動作そのものは今回の対象外)。

## 3. システム構成

### 3.1 全体像

ノードは dora-rs の `dataflow.yml` で配線する(`camera` → `vlm_planner` → `perception` → `policy` → `motion` → `robot`、ほかに `evaluator` と `recorder`)。ノードは薄い入出力の殻で、処理は dora に依存しないライブラリとして分け、単体テストできるようにした。詳細は [design.md](design.md)。

| 部品 | 役割 | 差し替え口 |
|---|---|---|
| `VlmClient` | 画像と指示から、対象と置き場所の検出枠(JSON)を返す | Anthropic / OpenAI / Gemini / Gemma(Ollama)を、設定(`configs/vlm.yaml`)で切り替え |
| `perception` | 検出枠の中心 + 深度 → ロボット座標の 3 次元位置 | キャリブレーション(sim はシーン定義から自動生成) |
| `Policy` | 3 次元位置から関節軌道を作る(v1 は IK = 減衰最小二乗法) | v2 で SmolVLA に差し替える口(未実装) |
| 安全フィルタ | 関節角・速度の上限、作業範囲の外の目標を拒否 | 実機の初回は速度 30% 以下の前提(実機は未実施) |
| `Robot` | 関節指令の送信と状態の取得 | `SimRobot`(実装済み)/ `So101Robot`(未実装) |
| `Evaluator` | 成功判定(箱の内側・縁より低い・静止) | sim 実装 `SimEvaluator`。実機版は別途 |
| `recorder` | 試行を LeRobot 形式(v3.0)で記録 | v2 のデモ収集と同じ形式 |

### 3.2 試行の流れ(1 回)

1. シードからブロックの配置を決める(20 cm 四方、ブロック同士 5 cm 以上離す。乱数は固定でき、同じシードなら同じ配置)。
2. 固定カメラで RGB と深度を撮る。
3. VLM に画像と指示を渡し、対象(pick)と置き場所(place)の枠を受け取る。座標の表現は各社で違うので、各クライアントの中でピクセル座標に統一する。
4. 枠の中心と深度の中央値から、ロボット座標の 3 次元位置を求める。
5. IK で `pre_grasp → grasp → lift → pre_place → place → retreat` の軌道を作り、安全フィルタを通して実行する。
6. 真のブロック位置で成功判定し、失敗は種類(VLM / IK / 把持 / 配置)で分類して記録する。

## 4. 工夫した点

1. **VLM の差し替えと、座標形式の吸収**: 4 社で座標の表現が違う(Anthropic は絶対ピクセル、Gemini と Gemma 4 は 0〜1000 に正規化した `[ymin, xmin, ymax, xmax]`、OpenAI は規定なし)。共通のスキーマと JSON 検証を置き、各クライアントの内部でピクセルに変換する([vlm-providers.md](notes/vlm-providers.md))。キーのないプロバイダは起動時に変数名つきで止め、評価では「未評価」と書く(成功率 0% と誤解させない)。
2. **VLM の失敗では、ロボットを動かさない**: JSON が不正・対象が見つからない・呼び出しの失敗では、動作せずに理由を表示する。実 VLM で、存在しない色(purple)を指示すると「紫のブロックは見えない」と返り、ロボットは動かなかった(AC-02)。一方で、**実 VLM は近い色で代用することがあった**(紫の指示で青いブロックを選ぶ)。そこでプロンプトに「色は厳密に一致させる。代用しない」を明記し、プロンプトを変えたらキャッシュが無効になる版数を持たせた。
3. **oracle(擬似 VLM)を基準線にした**: 真の配置から作った枠を返す偽の VLM を用意し、API キーなしで全体を通せるようにした。パイプラインの上限を見る基準にもなる(実 VLM の成績と分けて読める)。**動画では、oracle の枠が本物の VLM の検出に見えないよう、「VLM: oracle(擬似)」と表示する**。
4. **失敗の分類と、再現できる評価**: 失敗を VLM / IK / 把持 / 配置に分け、試行ごとに CSV に残す。シード・指示・色を固定し、全プロバイダで同じ条件にした。VLM の応答はキャッシュし、同じ画像・指示では API を呼び直さない。
5. **実 API の事故を防ぐ**: クレジット切れ(HTTP 429)は待っても直らないので再試行しない。トークン使用量を記録する。実 API を呼ぶ実行は、料金の目安を出して確認を取る(`--yes` で省略。非対話は拒否)。
6. **真値と方策を分ける(改修)**: 評価用の真値(ブロック・箱の位置)を `GroundTruth` 経由でだけ得て、方策側(`policy/`・`perception/`)には渡さない。この向きを、import を走査するテストで保証している。箱の位置を定数から試行ごとの `Scenario` に変え、箱を動かしても判定・oracle・計画が追従する(次節の掃引)。
7. **環境が許さない場所での検証**: 開発機は MuJoCo の DLL が使えなかったため、CI(GitHub Actions)と、一回限りの使い捨てワークフロー(ソフトウェア描画)で、実 MuJoCo のテスト・評価・動画の生成を行った。

## 5. 評価結果

条件: 20 試行 / プロバイダ、シード 0〜19、色は red・blue・green の順、指示は `put the {colour} block into the box`。詳細と注記は [provider-comparison.md](notes/provider-comparison.md)。

### 5.1 プロバイダ比較(AC-01 / AC-04 / AC-05)

| プロバイダ | モデル | 状態 | 成功率 | 検出誤差 平均 / 中央値 [mm] | IK 失敗 | 把持失敗 | 配置失敗 | VLM 時間 平均 [s] |
|---|---|---|---|---|---|---|---|---|
| oracle(参考。VLM ではない) | ground-truth | 評価済み | 85.0%(17/20) | 7.9 / 7.8 | 2 | 1 | 0 | 0.00 |
| **openai** | gpt-6-luna | 評価済み | **80.0%(16/20)** | 9.0 / 8.8 | 2 | 2 | 0 | 2.76 |
| anthropic | claude-haiku-5-5 | **未評価**(API キーなし) | - | - | - | - | - | - |
| gemini | gemini-3.8-flash | **未評価**(API キーなし) | - | - | - | - | - | - |
| gemma(Ollama) | gemma4:e4b | **未評価**(クライアントは実装し、偽サーバでテスト済み。実機のモデルでの検出は未確認) | - | - | - | - | - | - |

- **AC-01(成功率 70% 以上)は、OpenAI で満たした(80.0%)**。基準は暫定目標。
- OpenAI のトークンは入力 13,940 / 出力 2,638(20 試行)。料金は約 $0.003(実測)。
- 検出誤差には、枠が完全でも出る深度方式の偏り(約 6〜9 mm。斜めのカメラで枠の中心画素の深度が側面に当たる)が含まれる。oracle の 7.9 mm がその目安。**OpenAI の 9.0 mm は、oracle との差が約 1 mm** で、枠の精度は高かった。
- oracle と OpenAI で IK 失敗が同数(2)なのは、失敗の主因が VLM でなく**ブロックの配置**にあることを示唆する(失敗した seed が同じかは、この表からは確認していない)。固定位置の調整の記録では、作業範囲の手前端(x が小さい側。ロボットの付け根に近い)の配置で IK が収束せず、動作前に拒否された(FR-06。把持の問題ではない)。把持の調整(摩擦・質量・`forcerange`)は、固定位置で計画可能な配置が 29/29 で安定したため変更しなかった([grasp-tuning.md](notes/grasp-tuning.md))。
- **各プロバイダ 20 試行なので、1 件の差は 5 ポイント**に当たる。oracle と OpenAI の差(85% と 80%)は、この件数では有意とは言えない。

### 5.2 箱の位置を動かした評価(改修の確認)

箱を 3x3 の位置に動かし、各点 10 試行(oracle)を実行した結果は、**88 / 90(98%)**。置きの失敗は 0 件で、成功判定が動いた箱に追従している([box-sweep.md](notes/box-sweep.md))。ただし次の限界がある。

- 箱を動かせたのは約 2 cm × 5 cm(x 0.18〜0.20、y 0.13〜0.18)と狭い。安全フィルタの作業範囲・IK・箱の壁とのすき間・ブロックとの共存で決まる(作業範囲は安全の設定なので広げていない)。
- 箱に近すぎるブロック配置の seed は除いて集計したため、基準の 85% とは直接比較できない(「箱の位置で成績が悪化しない」ことの確認であって、成功率の改善ではない)。
- 箱固定の既定では、`Scenario` に切り替えた後も oracle が 85.0%(17/20)・検出誤差 7.9 / 7.8 mm のまま、従来と完全に一致した。

### 5.3 品質

- 単体・統合テスト 2,000 件超が CI で通り、カバレッジは約 92%(基準 80%、AC-07)。実 API と描画のテストは、CI では除外し(印付き)、描画のできる環境で別に実行した。
- 実行環境: GPU なしで、oracle の 20 試行は約 25 秒(AC は 1 試行 3 分以内)。

### 5.4 動画(AC-06)

oracle(擬似 VLM)による下書きの動画(約 1 分 29 秒、2 倍速)を作った。指示・段階(指示 → 検出 → 実行 → 判定)・検出枠・判定・「2倍速」の表示が映る。**提出用は、実際の VLM(OpenAI)の枠で作り直す**(未完了)。

### 5.5 v2(SmolVLA)の比較表

**v2 は実施していない**(実機が必要)ため、IK 版と SmolVLA 版の比較表は無い。

| RoboOps | 検証、CI | 試行の自動評価(`run_eval.py`)、GitHub Actions でテストとカバレッジ | 実施 |

### 6.1 macOS でのデバイス固定(講義第 3 回の udev の代わり)— **方針のみ、未実施**

実機の PC は macOS で、udev は Linux の機能なので使えない。代わりに、USB の**シリアル番号**で機器を特定する方針を立てた(TASK-0033)。

- フォロワー・リーダーのアーム: pyserial のポート一覧からシリアル番号で `/dev/cu.*` を探す。設定(`configs/real.yaml`)には、ポート名でなくシリアル番号を書く。
- カメラ: 名前などで特定する。
- 確認する項目: 抜き差し・再起動のあとも同じ対応になること。

実機を接続していないため、この方針は**実機で未確認**。

### 6.2 ROS 2 への移植方針 — **方針のみ、未実装**

ROS は必須でなく、今回は使っていない。移植するなら次の対応になる。

| 本課題 | ROS 2 |
|---|---|
| dora-rs のノード(`camera` / `vlm_planner` / `perception` / `policy` / `motion` / `robot` / `evaluator`) | 同名の ROS 2 ノード。`dataflow.yml` の配線は、トピックとサービスに置き換える |
| `rgb` / `depth` / `intrinsics` | `sensor_msgs/Image`(深度は 32FC1)と `CameraInfo` |
| `detections`(検出枠、ピクセル) | 独自メッセージ(または `vision_msgs/Detection2DArray`) |
| `targets_3d` | `geometry_msgs/PointStamped`(フレームは `baseframe`) |
| `joint_trajectory` / `joint_command` / `robot_state` | `trajectory_msgs/JointTrajectory` / `JointState` |
| `Robot` 抽象(`SimRobot` / `So101Robot`) | `ros2_control` のハードウェアインターフェース |
| `Policy` 抽象 | 方策ノード(IK は MoveIt に置き換えられる) |

ノードの中身(座標変換、IK、成功判定、JSON 検証)は、dora に依存しないライブラリとして分けてあるので、そのまま再利用できる。差し替えが必要なのは、入出力の殻と、ドライバだけ。

## 7. 今後の課題

1. **v2(実機)**: `So101Robot` の実装、実機カメラのキャリブレーション、リーダーアームによるデモ収集(50 本以上)、SmolVLA の微調整、IK 版との実機比較。実機の安全(非常停止、初回は速度 30% 以下、通信途絶で停止)は設計済みで、実機では未確認。
2. **未評価のプロバイダ**: Anthropic・Gemini は API キーを用意して評価する。Gemma(Ollama)は、メモリの収まる環境で `gemma4:e4b` の検出精度と使用メモリを測る。
3. **提出用の動画**: 実際の VLM(OpenAI)の枠で作り直す。
4. **箱の位置の自由度**: 現状は約 2 cm × 5 cm。安全フィルタの作業範囲(実機にも効く設定)を見直せば広げられる。また、到達可能領域の格子(1 cm)を細かくすれば、保守的な判定を減らせる。箱の向き(yaw)は対象外のまま(枠の検出では向きが取れない)。
5. **実 VLM での箱位置の評価**: `--box-xy` を実装済み(料金の目安と確認つき)。OpenAI で箱を動かした再評価は未実行。
6. **付け根に近いブロックの IK 失敗**: 失敗の主因。ブロックの配置範囲の見直しか、IK の初期値・姿勢拘束の改善で減らせる可能性がある。
7. **評価の件数**: 各プロバイダ 20 試行は、プロバイダ間の差を断定するには少ない。件数を増やし、信頼区間を付ける。
8. **ROS 2 / Docker**: 6.2 の移植方針の実装と、Docker 化。
