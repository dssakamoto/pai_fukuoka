# scenario-ground-truth 要件定義書

## 概要

SO-101 + VLM の pick & place (MuJoCo) は v1 で完成している (oracle 85%、OpenAI 80%)。しかし「箱の位置は固定」という前提が定数 `SCENE_SPEC.box_center_xy` (`src/so101_vlm/eval/scene_spec.py`) として複数箇所に散らばっている。箱を動かすと、成功判定 (`eval/judge.py`)、oracle (`eval/oracle_vlm.py`)、固定位置デモ (`eval/fixed_pick.py`) が元の位置を見続けて壊れる。VLM 版 (`eval/trial.py` の `estimate_goal`) は画像から箱の xy を求めるので追従できるが、置く高さは固定値 `box_floor_top_z` である。また `configs/motion.yaml` の workspace と `obstacle_geoms` は手書きである。

本 plan では次の設計に改める。

1. シーンを 3 つに分ける。`SceneGeometry` (形状=定数、XML から読む)、`Scenario` (試行ごとの配置=状態)、`GroundTruth` (評価・デバッグ専用の真値ビュー)。
2. 方策 (VLM→IK) が見てよい情報を `Observation` 型で制限し、真値は `GroundTruth` 経由の 1 本の経路だけにする。依存の向きは pytest で検査する。
3. 配置生成を `sample_scenario(seed, spec) -> Scenario` の 1 責務にする。箱は `Fixed | UniformXY` で切り替え、既定は `Fixed`。
4. 置き先を「領域」として扱い、判定も同じ領域を使う。置く高さは `SceneGeometry` から求める。
5. 障害物はモデルのタグ/グループから自動収集し、作業範囲はロボット運動学から導く。
6. 変換不変性・XML 整合・箱位置ごとの成功率掃引をテストとレポートに載せる。
7. `Evaluator` を Protocol にし、sim 実装を提供する。

## 用語集

| 用語 | 定義 |
|-----|------|
| SceneGeometry | 形状 (箱の内寸・縁の高さ・床面高さ、ブロック寸法など) の定数。`assets/scene_pickplace.xml` の名前付き geom から読み、Python に数値を再掲しない |
| Scenario | 試行ごとの配置 (ブロックと箱の姿勢)。シードから生成される状態。frozen dataclass |
| GroundTruth | Scenario/シミュレーションから作る真値のビュー。評価・デバッグ専用 |
| Observation | 方策が見てよい情報。RGB・深度・指示・関節角のみ |
| ScenarioSpec | 配置生成の仕様。`box` に `Fixed(...)` または `UniformXY(...)` を取る |
| 置き先領域 | 箱の位置・内寸・縁の高さからなる領域。置く目標と成功判定で共有する |
| Evaluator | 試行の成否を判定する Protocol。sim 実装は状態から自動判定する |
| oracle | 真値から作る擬似 VLM。VLM の上限性能の目安 |
| 変換不変性 | 箱を動かしても oracle・判定の結果が (相対的に) 変わらず追従する性質 |
| 到達可能領域 | ロボットの運動学から導いた、エンドエフェクタが届く作業範囲 |
| yaw | 箱の鉛直軸まわりの向き。本 plan の対象外 |

### 普遍要件 (SHALL)

- **FR-001**: システムは `SceneGeometry` を `assets/scene_pickplace.xml` の名前付き geom から読み込まなければならない 🔵 *設計方針1*
  - 関連: US-003, AC-001
- **FR-002**: システムは試行ごとの配置 (ブロックと箱の姿勢) を frozen dataclass の `Scenario` として表現しなければならない 🔵 *設計方針1、既存流儀*
  - 関連: US-001, AC-002
- **FR-003**: システムは `Scenario`/シミュレーション状態から評価・デバッグ専用の `GroundTruth` ビューを作らなければならない。真値を取得する経路はこの 1 本のみとする 🔵 *設計方針1,2*
  - 関連: US-004, AC-003
- **FR-004**: システムは方策に渡す情報を `Observation` 型 (RGB・深度・指示・関節角のみ) に限定しなければならない 🔵 *設計方針2*
  - 関連: US-004, AC-004
- **FR-005**: システムは置き先を点でなく領域 (箱の位置・内寸・縁の高さ) として扱い、成功判定にも同じ領域を使わなければならない 🔵 *設計方針4*
  - 関連: US-002, AC-005
- **FR-006**: システムは置く高さを固定値でなく `SceneGeometry` の箱形状から求めなければならない 🔵 *設計方針4*
  - 関連: US-002, AC-006
- **FR-007**: システムは `Evaluator` を差し替え可能な Protocol として定義し、sim 実装 (状態から自動判定) を提供しなければならない 🔵 *設計方針7*
  - 関連: US-009, AC-007
- **FR-008**: システムは障害物 geom をモデルのタグ/グループから自動収集しなければならない (`configs/motion.yaml` の `obstacle_geoms` 手書き列挙を廃止) 🔵 *設計方針5*
  - 関連: US-006, AC-008
- **FR-009**: システムはロボットの運動学から到達可能領域を導いて作業範囲として保持し、シーン配置側がそれに従わなければならない 🔴 *設計方針5。導出方法 (サンプリング/IK 格子など) は未決*
  - 関連: US-007, AC-009
- **FR-010**: システムはブロックと箱を同時に制約つき (間隔・箱とブロックが重ならない・作業範囲内) で生成する純関数 `sample_scenario(seed, spec) -> Scenario` を提供しなければならない 🔵 *設計方針3*
  - 関連: US-001, AC-010
- **FR-011**: システムは `ScenarioSpec.box` を `Fixed(...) | UniformXY(...)` で切り替えられるようにし、既定を `Fixed` にしなければならない 🔵 *設計方針3、スコープ決定*
  - 関連: US-001, AC-011

### イベント駆動要件 (WHEN-THEN)

- **FR-101**: `box=Fixed` で同じ seed を与えた場合、システムは既存の `sample_layout` と同じブロック配置を返さなければならない (乱数の消費順序を変えない) 🔵 *スコープ決定: 再現性*
  - 関連: US-010, AC-012
- **FR-102**: 箱の位置が `Fixed` の位置から動かされた場合、システムは成功判定・oracle・固定位置デモが新しい箱位置に追従して動作しなければならない 🔵 *背景・設計方針6*
  - 関連: US-002, AC-013
- **FR-103**: 生成した箱の位置が、箱を置く軌道を計画できない場合(安全フィルタの workspace の外、または pre_place / place の IK が解けない)、システムはその位置を棄却して再生成しなければならない 🔵 *設計方針3。ブロックは棄却しない(plan.md の G1 (b)。実測で付け根付近に掴めない領域があり、ブロック側は従来から計画失敗として扱われる)*
  - 関連: US-001, US-007, AC-014
- **FR-104**: 再生成の試行上限に達した場合、システムは `ValueError` (または専用例外) を送出しなければならない 🟡 *既存のエラー処理流儀。上限回数は設計で決定*
  - 関連: US-001, AC-015
- **FR-105**: 箱位置の掃引評価を実行した場合、システムは箱位置ごとの成功率を集計し、レポートに載せられる形式で出力しなければならない 🔴 *設計方針6。掃引の格子・合格基準は未決*
  - 関連: US-008, AC-016
- **FR-106**: `policy/` または `perception/` が `eval/` または `scene_spec` を import した場合、システムは pytest を失敗させなければならない (ast による import 走査) 🔵 *設計方針2、スコープ決定*
  - 関連: US-005, AC-017

### 状態駆動要件 (WHERE)

- **FR-201**: 箱が `Fixed` の間、システムは既存の評価結果 (同 seed で同じ成功率、`docs/notes/provider-comparison.md` の比較表) を変えてはならない 🔵 *スコープ決定: 再現性*
  - 関連: US-010, AC-018
- **FR-202**: VLM 試行の間、システムは目標の xy を画像 (箱の枠) から、置く高さを `SceneGeometry` から求めなければならない 🔵 *背景 (estimate_goal)、設計方針4*
  - 関連: US-011, AC-019

### 任意要件 (MAY)

- **FR-301**: システムは箱位置の掃引を実行するスクリプト (`scripts/` 配下) を提供してもよい 🟡 *設計方針6の運用手段として推測*
  - 関連: US-008, AC-020
- **FR-302**: システムは実 API (OpenAI) による再評価を任意の確認タスクとして提供してもよい 🔵 *非機能・制約 (料金)*
  - 関連: US-012, AC-021

### 禁止要件 (MUST NOT)

- **FR-401**: `policy/` と `perception/` は `eval/` および `scene_spec` を import してはならない 🔵 *設計方針2*
  - 関連: US-005, AC-022
- **FR-402**: システムは方策 (VLM→IK) に `GroundTruth` を渡してはならない 🔵 *設計方針2*
  - 関連: US-004, AC-023
- **FR-403**: システムは XML の名前付き geom が持つ数値を Python に再掲してはならない (整合は `tests/test_scene.py` が照合する) 🔵 *設計方針1、既存テスト維持*
  - 関連: US-003, AC-024
- **FR-404**: 純粋ロジックは入力を変更してはならず、グローバルな乱数・時計を使ってはならない (seed を引数に取る) 🔵 *既存流儀 (context.md)*
  - 関連: US-010, AC-025

### 対象外 (Won't)

- 箱の向き (yaw) のランダム化。bbox 方式では yaw が取れないため、将来課題としてレポートの「今後の課題」に記す
- 実機向け Evaluator の実装 (Phase 5 以降の別 plan)。本 plan は Protocol と sim 実装まで
- import-linter 等の新規依存の導入
- 実 API を使う再評価を必須の受入基準にすること
